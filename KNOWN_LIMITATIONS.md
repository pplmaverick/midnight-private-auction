# Known Limitations

This document records items found during self-audit of `contract/src/auction.compact` that were
evaluated and judged not to need a fix (or that have already been fixed), along with the reasoning
behind each judgment — for future maintenance or external review.

---

## 1. Salt uniqueness is not enforced on-chain

**Status:** Resolved by design (not a weakness)

`bidSalt` is generated by the frontend on every `placeBid` call via
`crypto.getRandomValues(new Uint8Array(32))`. The contract itself does not enforce that this salt
is unique.

This does not create a real risk, because:
- `computeCommitment`'s hash input includes `auctionId`, so commitments across different auctions
  never collide even if the same salt were reused.
- Within a single auction, two different bidders using the same salt does not benefit or harm
  either party — each commitment is still checked only against its own `bidderPK` entry in
  `sealedBids`, so a matching salt between two unrelated bidders has no effect on either one's
  outcome.

## 2. bidderPK was correlatable across auctions

**Status:** Fixed (this round)

Before the fix, `bidderPublicKey(sk)` produced the same output for a given `sk` across every
auction, letting an on-chain observer correlate the same identity's bidding behavior across
multiple auctions. This has been changed to `bidderPublicKey(sk, auctionId)`, folding `auctionId`
into the hash input, so the same user's `bidderPK` now differs between auctions. Verified via
Independent Reference Model Testing (`bidderpk_auctionid_isolation`, 300 cases, MATCH — see
`verification/REPORT.md`).

(`auctioneerPublicKey` intentionally remains correlatable across auctions: since `createAuction` is
open to anyone with no admission barrier, a stable and traceable auctioneer identity acts as a
lightweight reputation mechanism, letting bidders look up the same seller's auction history.)

## 3. No escape hatch for auctioneer neglect

**Status:** Known limitation, accepted risk (not addressed at this time)

If an auctioneer creates an auction and never calls `closeAuction`, `phase` stays permanently in
`BIDDING` — there is no mechanism for a bidder to withdraw their sealed bid record or force the
auction's phase forward.

**Risk assessment:** `placeBid` does not lock any DUST or token as collateral (it only writes a
hash commitment), so there is no funds-at-risk in this scenario. The worst case is the gas already
spent and a local private-state bid record that can never be redeemed on-chain.

**Possible future fix direction (not implemented — a feature enhancement, not a bug fix):** allow
anyone to force-call `closeAuction` after `endTime` plus some grace period, instead of restricting
it to the auctioneer indefinitely.
